## 实验过程

操作时间：2026 年 9 月 29 日完成开发、验证和首次推送；9 月 30 日整理实验材料。仓库地址：https://github.com/lboverfys/HIS。

实际环境：Windows、Node.js v22.19.0、npm 10.9.3、Git 2.51.0.windows.1。AI 协作使用 Codex；课程原题列出 OpenCode，本次工具差异如实记录。项目使用原生 HTML、CSS、JavaScript 和 Node.js 内置 HTTP 服务，无第三方依赖。

需求：开发就诊记录列表，显示患者姓名、科室、诊断、就诊时间；点击进入详情，详情显示就诊编号、患者信息、科室、医生、时间和摘要，并可返回列表。数据为 6 条虚构教学记录，不连接真实医院系统。

计划：采用静态页面、浏览器原生模块和哈希路由，使用 npm run dev 启动。先建项目基础，再在个人分支开发，完成差异审查、功能验证、提交与合并。我在查看最小方案后确认从零开始，并明确授权本地提交、分支合并、专用分支回滚和推送。

Git 基础：执行 git init -b main，创建 .gitignore，包含 node_modules/、.env、.env.*、__pycache__/ 等规则；配置用户提供的 origin 地址。git add 将指定文件加入暂存区，git commit 保存快照。提交 3d2cb71 建立项目基础。

三区模型：工作区存放正在编辑的文件；暂存区保存本次准备提交的内容；仓库保存已提交的历史。git diff 查看工作区与暂存区的差异，git diff --cached 查看暂存区与当前提交的差异。额外在 README 中加入本次练习专用临时行，查看 diff 后用 git checkout -- README.md 还原，未影响其他文件。

分支开发：执行 git switch -c feature/visit-records，在该分支完成页面提交 dd5aa50 和自动测试提交 1b08636。实现后用 git diff 检查代码差异，并保存实际命令输出。

关键代码：src/records.js 保存固定数据，recordHash 生成详情地址，findRecordByHash 校验地址并定位记录；src/app.js 根据地址渲染列表、详情或不存在提示；hashchange 处理页面切换。src/styles.css 在窄屏切换为卡片式列表。server.mjs 只提供明确列出的静态文件，并仅监听 127.0.0.1。

功能验证：运行 npm run dev 后，通过 chrome-devtools MCP 逐条打开 6 条详情并返回，核对姓名与诊断，全部通过；浏览器前进、后退、详情刷新和无效编号提示通过。实测 390 px 窄屏下，列表与详情没有横向溢出；控制台未发现错误或警告。

回滚演练：从 1b08636 创建 exercise/rollback 分支，只在详情链接前加入错误前缀 BROKEN-，提交为 0059960。验证故障并截图后，核对仓库、分支和干净工作区，执行 git reset --hard 1b08636。再次从列表进入同一条记录，详情恢复，git diff 1b08636 --exit-code 返回成功。

恢复后迭代：切回 feature/visit-records，集中生成和解析详情地址，补充“链接能解析回原记录”和“错误地址不能返回患者”的回归测试，形成提交 89bc2f8。npm test 共 3 项通过，浏览器再次逐条验证 6 条记录通过。

分支合并：切回 main，执行 git merge --no-ff feature/visit-records，产生合并提交 233a935，无冲突。git log --oneline --graph --all --decorate 显示完整分支图，git branch --merged main 确认功能分支已合入；功能合并阶段已有 5 笔规范提交，满足至少 3 次的要求。

远程交付：执行 git push -u origin main 成功，首次推送后远程 main 与本地提交 233a9352336487c65a31e5022488d5cf006db4ea 一致。故障提交仅用于本地演练，未推送到 main。

性能与范围：仅有 6 条本地小型记录，无数据库查询和外部 API；详情在内存中查找，切换记录不逐条发起远程请求。没有新增依赖、全局配置或线上操作。

## 问题与解决

问题一：没有已有项目。处理：从独立目录建立项目，复用 D 盘已安装的 Node.js 与 Git，用内置功能实现，不安装第三方依赖。

问题二：故意给详情链接加入 BROKEN- 前缀，导致记录无法找到。处理：用 git diff 定位差异，用 git log 找到正常版本，在专用分支执行硬回滚；恢复后集中管理详情地址并补充回归验证。

问题三：截图工具不能直接写入项目路径，且一次全页截图超时。处理：仍使用 chrome-devtools 获取截图原始结果，保存到已授权的 D 盘目录；改用明确视口尺寸完成截图。

问题四：文档技能的 LibreOffice 转换组件不可用。处理：复用现有 WPS 的文档接口导出预览 PDF，再使用已有 Poppler 渲染页面进行排版检查，没有安装新的 Office 或运行时。

## 思考题一 没有 Git 的风险

Git 为 AI 辅助开发保留了可比较、可定位、可恢复的版本。AI 能很快修改代码，但仍可能误解需求或引入错误；如果只有一份不断覆盖的文件，出错后就难以知道改了哪里，也难以恢复到正常状态。

本次在 exercise/rollback 分支把详情地址加入 BROKEN- 前缀，产生故障提交 0059960。浏览器点击第一条记录后显示“未找到该就诊记录”。通过 git log --oneline 找到正常提交 1b08636，再执行 git reset --hard 1b08636，重新从列表点击后恢复为林晓禾的就诊详情。git diff 还帮助定位到具体改坏的一行。

因此，Git 能让试错有记录、修复有依据。操作前仍须明确仓库和分支，并保护未提交修改；本次只在独立演练分支、工作区干净时执行硬回滚。恢复之后还要重新验证，不能把命令执行成功当作功能已经正确。

## 思考题二 提交说明对比

对比示例：“完成页面”只说明做过修改，无法看出具体内容。实际采用的标题“功能：实现就诊记录列表与详情页面”明确了修改类型与范围；正文再分点写修改内容、修改原因、影响范围和验证结果，方便日后查找和回滚。

实际提交 dd5aa50 的正文：修改内容——新增六条虚构就诊记录、列表、详情、返回导航和窄屏布局；修改原因——完成患者姓名、科室、诊断、时间展示及详情跳转；影响范围——前端静态页面和教学数据；验证结果——语法检查通过，浏览器确认列表完整并能打开首条详情。

AI 可以根据真实差异起草提交说明，人需要核对说明与代码、测试结果是否一致，避免空泛表述或未验证的成功声明。本次标题和正文均使用中文，统一采用“类型：具体修改”的标题格式。

## 心得与反思

本次实验把需求、方案、代码、验证、提交串成了完整流程。页面能够显示只是第一步，还需要核对每条详情是否匹配，并验证返回、刷新和错误地址。AI 可以承担实现和检查，但需求范围、方案选择与操作权限仍需要人明确。

回滚演练让我理解了小步提交的价值：正常版本有明确编号，故障出现后可以先恢复可用状态，再分析原因并补上回归验证。分支将日常开发和故障演练分开，显式合并保留了过程，提交正文也帮助解释每一步为什么发生。

今后进行 AI 辅助开发时，我会先整理验收条件，再审查差异和测试结果；在已验证的节点提交，不把所有改动堆到最后一次提交，也不把“AI 说完成”当成实际验收。
